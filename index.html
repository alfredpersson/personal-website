What I do

I'm trained in interaction design, so I start with what the user is trying to get done, and I use error analysis to find where the product fails to deliver it.

What end-to-end ownership means, concretely:

Start from the user's problem.

I talk to users to understand what they are trying to get done, and use AI only where it is genuinely the best tool. AI inference is the slowest, most expensive, and least predictable way to solve a problem, so every part of a feature that can be ordinary software should be.

TechnicalJobs-to-be-done discovery; deterministic logic wherever possible; model calls reserved for the steps that need judgment or language.

Design the right kind of system for the task.

That can be a normal, predictable workflow that calls AI for specific steps, a system that searches your own data before answering, or an agent that plans and acts on its own. I pick the shape by the task, and keep everything around the AI boring and reliable.

TechnicalDeterministic workflows with LLM steps, RAG pipelines, tool-using agents, human-in-the-loop escalation, multi-tenant isolation.

Agree on what "working" means before building.

Before writing code, I collect real example inputs and write down what a correct result looks like for each one. Those examples become automatic checks that run on every change, showing whether each change made quality better or worse.

TechnicalHand-labeled eval sets with pass or fail criteria, run in CI as the regression suite.

Plan for the model being wrong.

A model will be wrong some of the time, so I design that moment on purpose: what the user sees, when the system says it is not sure, and when a human takes over. Every failure that shows up in production becomes another automatic check, so the same mistake cannot return unnoticed.

TechnicalConfidence gates, designed fallback and escalation paths, production errors converted into permanent CI test cases.

Measure whether it actually helps.

I track whether the feature helps in numbers: who uses it, whether it resolves what they came for, and how good the outputs are, checked by both humans and automated grading.

TechnicalProduction trace analysis, LLM-as-judge scoring validated against human grading, quality and usage metrics per release.

obligations-agent: EU AI Act and GDPR obligations for one AI product

in progress

A tool that takes the facts of one AI product from a short form and a few follow-up questions, and returns a memo with one row per obligation under the EU AI Act and the GDPR: the clause it comes from, what it means for that product, and one action. It is for engineers who know their system in detail and have no lawyer to ask. Role: Sole builder.

Ask with a form and fixed choices first, then let a model choose the follow-up questions inside limits set in code

Because the user knows their system and does not know the law, so the questions have to come from a fact schema written from the regulation text.

Measured bythe share of started intakes that reach a memo, and the share of 'not sure' answers per question

Decide which regulations, roles and risk tiers apply with rules in code, not a model

Because the same facts must always give the same result.

Measured bya benchmark of test products with known correct answers

Quote and link the clause in the official text on every row of the memo

Because a person who is not a lawyer has to be able to check each row.

Measured bythe share of rows that users mark as disputed, and hand labels of the written meaning and action

In production since July 2026

Integrated vs chat: a measured comparison

80.8% vs 64.2% action accuracy, integrated vs chat, on a 73-item eval

Teams default to a chat UI for AI features. Whether an integrated, structured interface actually performs better on the same workflow was an assumption I wanted numbers for. Role: Sole builder.

Hold the model constant and vary only the interface

Because otherwise interface effects are confounded with model quality.

Measured byaction accuracy on a 73-item hand-labeled eval set

Ground every claim with two independent judges (Claude Opus 4.7 and GPT-5)

Because a single judge bakes one model's bias into the results.

Measured bysubstring grounding rates per judge, 99.3% integrated vs 93.4% chat

Keep the eval run that failed, together with the fix and the run after it

Because a scorecard is only useful if it can catch a problem.

Measured byone recorded case: industry classification went from 32.9% to 94.5% after the fix

RAG support assistant with designed failure paths

71% hit rate at 5, 4.80/5 faithfulness, across 7 evaluation experiments

Support bots fail worst when they answer confidently from weak retrieval. I built a pipeline where every low-confidence path has a designed response instead of a guess. Role: Sole builder.

Classify every query into five categories before retrieval

Because a cancellation request must never get a how-to answer, and nonsense should not waste retrieval compute.

Measured byeach category routing to its own purpose-built response path

Gate answers behind two reranker confidence thresholds

Because generating from weak context erodes trust faster than asking a clarifying question.

Measured byfaithfulness and relevancy scores across 7 experiments (4.80/5 and 4.76/5)

Run a self-critique step after generation

Because the cheapest place to catch a partial answer is before the user sees it.

Measured bythe critique verdict deciding whether human escalation is offered

AI Feature Maturity Ladder

Five dimensions, five levels, weakest dimension sets the score

AI feature adoption problems get treated as prompt problems. Usually something else is holding the feature back, and teams have no structured way to find it. Role: Author. The framework is a synthesis; the dimension cuts and level rubric are my choices..

Score five dimensions independently and let the weakest set the level

Because a feature is constrained by its weakest dimension, not its average.

Measured bythe min-rule stated explicitly in the published rubric

Give every level both a user-visible signal and a team signal

Because a feature can look adopted while being operationally fragile, and the reverse.

Measured byboth signal columns present for all five levels

Make output quality one dimension of five, not the whole score

Because accuracy can improve while adoption stays flat.

Measured byfour of the five dimensions cover something other than output quality
